APPLE-INSPIRED DESIGN GUIDELINES
02. USER EXPERIENCE

Project: PDF-based University Exam Study Web App

==================================================
0. PURPOSE
==================================================

이 문서는 사용자가 앱을 실제로 사용하는 과정에서
무엇을 보고, 무엇을 누르고, 어떤 피드백을 받고,
각 상태가 어떻게 이어지는지를 정의한다.

01. PRODUCT STRUCTURE가 "무엇을 어디에 놓는가"를 정의했다면,
02. USER EXPERIENCE는 "사용자가 그것을 어떻게 경험하는가"를 정의한다.

시각적인 CSS 수치와 디자인 토큰은 03. VISUAL DESIGN SYSTEM에서 정의한다.


==================================================
1. CORE UX PRINCIPLE
==================================================

사용자는 앱의 내부 구조를 배울 필요가 없어야 한다.

사용자의 머릿속 흐름은 최대한 단순해야 한다.

"자료를 넣는다."
→ "시험을 만든다."
→ "푼다."
→ "채점된다."
→ "복습한다."

각 화면은 현재 행동에 집중시키고
다음 행동을 자연스럽게 알려줘야 한다.


==================================================
2. USER AGENCY
==================================================

사용자는 항상 자신이 무엇을 하고 있는지,
무슨 일이 일어나고 있는지,
다음에 무엇을 할 수 있는지 알 수 있어야 한다.

특히 시스템이 오래 걸리는 작업을 수행할 때:

- 현재 상태
- 진행 상황
- 예상되는 다음 단계

를 적절히 알려준다.

사용자의 행동을 막는 경우에는
왜 막혔는지도 설명한다.


==================================================
3. USER FLOW
==================================================

Primary Flow:

Home
↓
Upload PDF
↓
Configure Questions
↓
Generate
↓
Start Exam
↓
Answer Questions
↓
Submit
↓
View Results
↓
Review

이 흐름에는 불필요한 interruption을 넣지 않는다.

예를 들어 Exam 도중
사용자에게 별도의 기능을 홍보하거나
관련 없는 설정을 보여주지 않는다.


==================================================
4. INTERACTION PRINCIPLES
==================================================

모든 interactive element는
사용자가 "눌렀다"는 사실을 이해할 수 있어야 한다.

필수 상태:

- Default
- Hover
- Focus
- Active / Pressed
- Selected
- Disabled
- Loading
- Success
- Error

상태가 바뀌었을 때
사용자는 결과를 즉시 이해할 수 있어야 한다.

특히 선택지의 경우:

Default
→ Hover
→ Selected
→ Submitted
→ Correct / Incorrect

같은 일관된 상태 흐름을 사용한다.


==================================================
5. FEEDBACK
==================================================

사용자 행동에 대한 feedback은
행동과 가까운 곳에서 제공한다.

좋은 예:

파일 업로드 직후
→ 파일명과 업로드 상태 표시

답 선택 직후
→ 선택 상태 표시

시험 제출 직후
→ 채점 진행 상태 표시

좋지 않은 예:

사용자가 버튼을 눌렀는데
아무 변화가 없다가
몇 초 뒤 갑자기 화면이 바뀌는 것.

시스템이 처리 중이라면
즉시 processing state를 보여준다.


==================================================
6. PROGRESSIVE DISCLOSURE
==================================================

처음부터 모든 정보를 보여주지 않는다.

사용자가 필요한 순간에
필요한 정보만 제공한다.

예:

Upload 단계:
파일 업로드에 집중

Setup 단계:
문제 유형 / 개수 / 난이도에 집중

Exam 단계:
문제 / 답 / navigation에 집중

Results:
점수 / 결과 / 설명에 집중

Review:
정답 / 답변 / 설명에 집중

이 원칙을 통해 화면의 인지 부하를 낮춘다.


==================================================
7. LOADING EXPERIENCE
==================================================

Loading은 단순히 spinner 하나를 띄우는 것으로 끝내지 않는다.

긴 작업은 단계적인 상태를 사용한다.

PDF processing:

Uploading
→ Processing PDF
→ Reading Content
→ Preparing Questions

Question generation:

Generating Questions
→ Checking Questions
→ Preparing Exam

사용자는 시스템이 멈춘 것인지
작업 중인 것인지 구분할 수 있어야 한다.

단, 내부 구현에 필요하지 않은
세부적인 진행률을 가짜로 표시하지 않는다.

실제 진행률을 알 수 없다면
명확한 상태 메시지를 사용하는 것이 낫다.


==================================================
8. SKELETON VS SPINNER
==================================================

콘텐츠 구조가 이미 정해져 있고
곧 데이터가 들어오는 경우:

Skeleton

사용.

예:

Results 화면에서
결과 데이터가 잠시 늦게 오는 경우.

처리 과정 자체가 길고
결과 구조를 예측하기 어려운 경우:

Progress / Status indicator

사용.

모든 loading 상황에서
무조건 spinner 하나를 사용하는 것은 피한다.


==================================================
9. UPLOAD UX
==================================================

Upload 상태:

1. Idle
2. Drag Over
3. File Selected
4. Uploading
5. Processing
6. Complete
7. Error

Idle:

사용자가 무엇을 해야 하는지 명확하게 설명한다.

Drag Over:

파일을 놓을 수 있는 상태임을 명확하게 보여준다.

File Selected:

선택된 파일의 이름과 기본 정보를 보여준다.

Uploading / Processing:

현재 상태를 보여준다.

Complete:

다음 단계 CTA를 명확히 제공한다.

Error:

문제 원인을 이해할 수 있는 메시지와
재시도 방법을 제공한다.


==================================================
10. QUESTION GENERATION UX
==================================================

문제 생성은 사용자가 가장 불안해하기 쉬운 비동기 작업이다.

따라서:

"무언가 진행되고 있다"

는 느낌보다

"무엇을 하고 있고, 끝나면 무엇을 할 수 있다"

는 이해를 제공해야 한다.

권장:

Preparing your exam
Reading your PDF
Generating questions
Finishing up

한국어 UI라면 자연스러운 한국어로 표현한다.

과도하게 기술적인 문구는 피한다.


==================================================
11. EXAM UX
==================================================

Exam은 집중을 최우선으로 한다.

기본 interaction:

Question
→ Answer
→ Next

사용자가 문제를 읽는 동안
불필요한 animation이나 변화가 없어야 한다.

답을 선택하면
선택 상태가 명확하게 유지되어야 한다.

Next를 누르면
다음 문제로 자연스럽게 이동한다.

마지막 문제에서는:

Next
대신
Submit / Finish

등 명확한 완료 행동을 제공한다.


==================================================
12. EXAM NAVIGATION
==================================================

Previous:

사용자가 이전 문제로 돌아갈 수 있게 한다.

Next:

현재 문제의 답변을 유지한 채
다음 문제로 이동한다.

Submit:

전체 시험을 제출한다.

제출 전에 필요한 경우
간단한 confirmation을 제공한다.

예:

"아직 답하지 않은 문제가 있습니다."

이런 중요한 상태는 사용자가
실수로 시험을 종료하지 않도록 알려준다.


==================================================
13. ANSWER PERSISTENCE
==================================================

사용자가 문제를 이동해도
이미 입력한 답변은 유지되어야 한다.

특히:

- Short Answer
- Subjective

에서 중요하다.

브라우저 화면 크기 변경,
문제 이동,
일시적인 UI 상태 변화 때문에
사용자가 입력한 답이 사라지면 안 된다.


==================================================
14. AUTOSAVE / DATA SAFETY
==================================================

사용자가 작성한 답변은
가능한 한 즉시 애플리케이션 상태에 반영한다.

서버 저장이 필요한 경우에도
LLM 호출이나 네트워크 작업보다 먼저
사용자 답변을 저장한다.

특히 Subjective grading에서는:

User Answer
→ Save Answer
→ Call LLM
→ Receive Grade
→ Save Grade

순서를 기본으로 한다.

LLM 오류가 발생하더라도
사용자의 답변을 잃어버리지 않아야 한다.


==================================================
15. SUBJECTIVE GRADING UX
==================================================

서술형 답안 채점은
사용자에게 긴 AI 답변을 보여주는 기능이 아니다.

핵심 결과:

Score
Feedback

필요한 경우:

Criteria-level result
Model Answer

를 제공한다.

예:

4 / 5

핵심 개념은 정확하지만
삼투압과 농도 차이의 관계에 대한 설명이 부족합니다.

피드백은 짧고 구체적이어야 한다.

채점 결과를 사용자가 이해하는 데
불필요한 장문의 AI 문장을 사용하지 않는다.


==================================================
16. ERROR UX
==================================================

Error는 사용자를 탓하지 않는다.

나쁜 예:

"Invalid input."

좋은 방향:

"문제를 생성하지 못했습니다.
잠시 후 다시 시도해 주세요."

가능하면:

- 무엇이 실패했는지
- 다시 시도할 수 있는지
- 현재 데이터가 보존되어 있는지

를 알려준다.

기술적인 오류 코드는
일반 사용자에게 기본적으로 노출하지 않는다.


==================================================
17. API / LLM ERROR UX
==================================================

LLM API는 외부 시스템이므로
항상 실패할 가능성을 고려한다.

처리해야 할 상황:

- Timeout
- Rate Limit
- Network Error
- Invalid API Key
- Provider Error
- Malformed Response
- Unexpected JSON
- Temporary Server Error

사용자에게는 기술적인 오류보다
현재 가능한 행동을 알려준다.

예:

"문제 생성이 잠시 지연되고 있습니다.
다시 시도해 주세요."

개발자 로그에는
구체적인 provider/model/error 정보를 남긴다.

API key나 민감한 정보는
사용자 화면에 표시하지 않는다.


==================================================
18. RETRY UX
==================================================

Retry는 오류가 발생한 곳과 가까운 위치에 둔다.

예:

Generation failed
[Try Again]

Grading temporarily unavailable
[Retry Grading]

사용자가 처음부터 모든 과정을 다시 해야 하는
구조는 피한다.

이미 업로드한 PDF나 작성한 답변을
불필요하게 다시 입력하게 만들지 않는다.


==================================================
19. EMPTY STATES
==================================================

데이터가 없을 때
단순히 빈 화면을 보여주지 않는다.

Empty State는:

- 현재 무엇이 없는지
- 왜 없는지
- 사용자가 무엇을 하면 되는지

를 알려준다.

예:

아직 생성된 시험이 없습니다.

[PDF로 첫 시험 만들기]


==================================================
20. SUCCESS STATES
==================================================

성공 feedback은 명확하되 과장하지 않는다.

예:

PDF uploaded
Question generation complete
Exam submitted

과도한 confetti,
화려한 효과,
큰 축하 animation 등은 기본값으로 사용하지 않는다.

성공했다는 사실과
다음 행동이 중요하다.


==================================================
21. MOTION PRINCIPLES
==================================================

Animation의 목적은 장식이 아니라
상태 변화와 공간 관계를 이해시키는 것이다.

사용:

- 페이지 전환
- modal 등장/퇴장
- 선택 상태 변화
- progress 변화
- loading state
- expandable content

피함:

- 계속 움직이는 장식
- 의미 없는 bounce
- 과도한 spring
- 사용자의 집중을 방해하는 animation

Motion은 짧고 자연스러워야 한다.

사용자가 animation을 기다려야 하는 느낌을 주지 않는다.


==================================================
22. TRANSITIONS
==================================================

상태 변화는 갑자기 튀기보다
필요한 경우 짧은 transition을 사용한다.

예:

Default
→ Hover
→ Selected

Button
→ Loading
→ Complete

하지만 모든 요소에 transition을 넣지는 않는다.

콘텐츠 자체가 빠르게 바뀌어야 하는 경우
과도한 transition은 오히려 사용성을 떨어뜨린다.


==================================================
23. REDUCED MOTION
==================================================

사용자가 reduced motion을 요청한 환경에서는
불필요한 animation을 줄인다.

prefers-reduced-motion을 존중한다.

기능 자체는 유지하되
장식적인 movement는 최소화한다.


==================================================
24. ACCESSIBILITY
==================================================

접근성은 별도 기능이 아니라
기본 UX의 일부로 취급한다.

필수:

- 충분한 text contrast
- keyboard navigation
- visible focus state
- semantic HTML
- 적절한 button / input semantics
- color만으로 상태를 전달하지 않기
- 충분한 touch target
- text scaling 대응
- 자연스러운 wrapping

특히 한국어와 영어가 섞인 문제에서도
텍스트가 잘리지 않아야 한다.


==================================================
25. KEYBOARD UX
==================================================

Desktop에서 keyboard만으로도
핵심 흐름을 수행할 수 있어야 한다.

예:

Tab
→ interactive element 이동

Enter / Space
→ button / option interaction

Text input
→ answer 작성

가능한 경우
자연스러운 keyboard flow를 제공한다.

Focus가 어디에 있는지
항상 명확해야 한다.


==================================================
26. MOBILE UX
==================================================

Mobile에서는 desktop UI를 단순 축소하지 않는다.

원칙:

- single column
- 충분한 여백
- 큰 enough touch target
- 자연스러운 text wrapping
- 화면을 가리는 불필요한 fixed UI 최소화

Exam에서는:

Question
↓
Answer
↓
Navigation

순서가 자연스럽게 유지되어야 한다.

키보드가 올라왔을 때
입력창과 navigation이 가려지지 않도록 고려한다.


==================================================
27. RESPONSIVE BEHAVIOR
==================================================

Breakpoint를 단순히
"desktop / mobile" 두 개로만 생각하지 않는다.

레이아웃은 사용 가능한 공간에 따라
점진적으로 적응해야 한다.

예:

Wide desktop:
넓은 whitespace

Medium:
content width 감소

Tablet:
일부 layout collapse

Mobile:
single column

구체적인 breakpoint와 CSS 수치는
Visual Design System에서 정의한다.


==================================================
28. COGNITIVE LOAD
==================================================

사용자가 한 번에 처리해야 하는 선택의 수를 줄인다.

특히 Exam에서는:

- 메뉴 최소화
- 상태 최소화
- 선택지 명확화
- 다음 행동 명확화

를 우선한다.

사용자가 "다음에 뭘 해야 하지?"
라고 고민하게 만드는 UI는 좋지 않은 UX다.


==================================================
29. CONSISTENCY
==================================================

같은 의미는 같은 방식으로 표현한다.

예:

Primary action
→ 항상 동일한 visual hierarchy

Error
→ 동일한 feedback structure

Selected
→ 동일한 interaction pattern

Back
→ 일관된 위치/행동

사용자가 한 번 배운 interaction은
다른 화면에서도 그대로 적용되어야 한다.


==================================================
30. INTERRUPTION CONTROL
==================================================

사용자의 집중을 방해하는 요소는 최소화한다.

특히 Exam 중:

- modal 남발 금지
- toast 남발 금지
- 불필요한 notification 금지
- 자동 페이지 이동 최소화
- 갑작스러운 animation 금지

중요한 정보가 아닌 것은
사용자의 집중을 끊지 않는다.


==================================================
31. FINAL UX PRINCIPLE
==================================================

이 앱의 UX는 다음을 목표로 한다.

"사용자가 인터페이스를 생각하지 않고
공부 자체에 집중할 수 있게 한다."

좋은 UX는 사용자가
버튼과 메뉴를 인식하게 만드는 것이 아니라
자신이 하려는 공부를 자연스럽게 진행하게 만든다.

Apple-inspired UX의 핵심은
화려한 animation이나 유리 효과가 아니다.

명확한 목적,
사용자 통제,
익숙한 interaction,
적절한 feedback,
부드러운 전환,
접근성,
그리고 세부적인 상태 처리의 완성도다.
